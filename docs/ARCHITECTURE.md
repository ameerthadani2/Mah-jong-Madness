# Architecture

## Goals

1. **Play anywhere with friends** — private tables by code, like PokerBros, hosted by our game server and checked by every player.
2. **Checkable fairness** — every player's phone contributes to the shuffle and checks every hand it watched; the app says plainly what a phone could not check.
3. **Teach while you play** — the same analysis that drives the bots drives the coach.
4. **One rules engine everywhere** — the server's tables, offline bot tables on the phone, bots, drills and audits all run identical code.

## Layers

```
apps/mobile  ──┐
apps/signal  ──┼──▶ @mjm/net  (TableHost / TableClient / transports / fairness)
tests, sim   ──┘         │
                         ▼
                   @mjm/engine (GameState, applyAction, scoring, bots, hints)
```

### Engine (`packages/engine`)

* `tiles.ts` — 144 physical tiles (`TileId` 0..143) over 42 kinds (34 playable + 8 bonus).
* `hand.ts` — decomposition into 5 sets + pair, waits, shanten. Shanten is the distance to the nearest complete target (sets + pair) that holds at most four copies of any kind, so an un-konged quad is never read as a pong waiting on a fifth copy. It splits the hand into the three suits plus the honor block, computes each block's best overlap per (sets, pair) share with a small dynamic programme, and combines the four tables; tables are memoised by count signature. Fast enough for bot search on mobile (~40 ms per full hand of 4 bots).
* `scoring.ts` — `scoreWin(WinContext)` tries every decomposition and returns the max-台 breakdown. `computePayments` applies dealer 台 per transaction.
* `game.ts` — the JSON `GameState` and a pure `applyAction(state, seat, action)`. Phases: `discard` (player to act), `claim` (others respond to a discard or 加槓), `ended`. Drawing, flower replacement, kong replacement, dead-wall exhaustion and dealer rotation are internal transitions, so the only external inputs are player actions. `hashState`, `replayHand`, `matchSnapshot` support auditing.
* `view.ts` — `viewFor(state, seat)` strips other hands and the wall; `viewToState(view)` rebuilds an engine-shaped object so clients can run hints and legality checks on visible information only.
* `bot.ts` — shanten + acceptance ranking, simple danger model, claim policy. Also used for timeouts and disconnected seats.
* `rules.ts` — the `RuleSet` every table plays, its defaults, ranges and speed presets, and `sanitizeRules` for rules that arrive from outside (docs/RULES.md, "Rule options").
* `hints.ts` — coach text. `lessons.ts` and `lessons/` — the curriculum: 36 lessons in six tracks, with quizzes the engine checks.
* `puzzles.ts` — seeded puzzles in five themes (best discard, read the wait, defence, calling, value). `questions.ts` — a puzzle as its question: what a view needs before the answer and nothing that reveals or ranks it; `PUZZLE_FIELDS` classifies every field of every theme as shown or withheld (typed, so a new field must be classified). `rating.ts` — the puzzle rating. `review.ts` — replays a finished hand from its audit and grades each decision.

### Net (`packages/net`)

* **TableHost** owns the authoritative `GameState`, seats, timers and bots. It validates each action with the engine, broadcasts per-seat views, and publishes an `Audit` after every hand.
* **TableClient** joins, takes part in the ceremony, sends actions, keeps the latest view and verifies audits.
  Its code is split by concern. `client.ts` holds `TableClient` itself (the protocol, the link watch `checkLink`, saving and restoring, and the audit with its replay), the words of the audit (`AUDIT_CAVEATS`, `AUDIT_FAILURES` and their keys) and every check that writes one of those sentences, so `test/failure-text.test.ts`, which reads that file, sees all of them. `clientrecords.ts` holds the evidence the client keeps (the ceremony and play records of each hand, the saved copy `SerializedClient`), the guards on what the host sends and the match snapshot a hand starts from. `clientclock.ts` holds the client's own clock (`clientClock`), the time bounds of the link watch and the frame order, and what the client has learned of the host's clock (`foldClock`, `offsetFloor`). `clientmoves.ts` holds the rule the table plays a seat by (`tableRule`) and the check of when it may play this seat (`clockTrack`, `streakEnd`, `judgeTableMove`). `index.ts` exports from `client.ts` only, as before.
* **Fairness**: commit–reveal seed per hand (`fairness.ts`). The seed is derived only after all commitments are in; a seat that fails to reveal is replaced by a bot stand-in and the ceremony restarts, so a griefer cannot stall a table.
* **Transports** implement a 5-method interface: `LoopbackHub` (tests, offline bot tables) and `RelayTransport` (WebSocket relay via the game server, used by every online player). The server's table and the offline host each reach their players through a `Link`.
* **Hidden information**: clients only ever receive `TableView`s. The state hash in each update refers to the host's full state and is checked at audit time.

### Trust model

| Threat | Mitigation |
| --- | --- |
| Host rigs the shuffle | Seed is a hash of every seat's secret; commitments are published before any secret is revealed. |
| Host fakes actions or results | Action log + seed are published; each client replays and compares the hash and its own final hand. |
| Client sends illegal actions | Host validates against `legalActions`; errors are returned, state is re-sent. |
| Client acts for another seat | Peer id → seat binding; rejected. |
| Host peeks at the wall | Online tables are hosted only by the game server, never by a player's phone, so no player holds the wall. The server itself could still peek; the audit cannot detect that, and a mental-mahjong shuffle remains on the roadmap. |
| Player stalls or drops | Turn timers. A seat whose link drops keeps its turn clock and time bank like a connected one, so a short drop never costs a turn. When a seat's time runs out the table plays its own turn as a bot would, and answers an offer on another seat's discard with a pass unless the offer is a win: it never opens a player's hand for them. A dropped seat that has timed out once is then played at bot pace, by the same rule, until its player returns; a player who left on purpose or was removed is played at once. The seat is reclaimable with its rejoin token, and each client checks on its own clock that the table moved for its seat only after its time had run out (`docs/FAIRNESS.md`). |

### Clocks, time banks and game speeds

Each human seat that owes an action gets its own clock (`TableHost.clocks`), whether its link is up or has dropped: a base turn timer (`rules.turnSeconds`) and, once that expires, a per-hand time bank (`rules.timeBankSeconds`) that drains while they think. When the bank is empty the table plays for them by a fixed rule (a win is taken, any other claim is passed, a turn is played by the bot policy at Club strength or above from the seed `timeout:<seat>`), and each client recomputes those moves, and every bot's, at the audit (docs/FAIRNESS.md). Speeds are presets over those two numbers: Relaxed 30+60, Normal 15+30, Fast 10+20, Turbo 7+10, Hyper 4+0. The client receives its own deadline, remaining bank and an `inTimeBank` flag with every state update. The app counts the player's own clock itself (`TableClient.ownClock`, `useTurnCountdown`): the turn clock from the state that started the move, then the bank, placed on the phone's clock by the table's answers to its pings, so it goes on to the bank without waiting for the state that says so, and a wrong wall clock on the phone does not move it. It counts to the same end the audit holds the table to (`streakEnd`). Other seats' clocks are counted from their deadline.

While a hand is played the host never leaves a connected seat without a frame for more than 3 s: when it has sent nothing else, answers to the seat's pings aside, it sends a `clock` frame with the turn (`CLOCK_FRAME_MS`; the app pings once a second, and a link whose delay rose 8 s in one step would otherwise bring nothing for 11 s, past the heartbeat's 10 s), and its time stamps never go back. The online session asks its client every second whether the link has gone silent (`TableClient.checkLink`). The bound is the client's, not the server's: the watch always runs during play at the protocol's `CLOCK_FRAME_MS` (in `messages.ts`), whatever the `welcome` announces in `clockMs` (left out, or more than 3 s, counts as 3 s). When the newest stamp has fallen 8 s behind the phone's clock (twice the period, plus 2 s), measured against the least arrival offset of the frames that arrived in the last 20 s, never less than the least seen in this clock era, run of the app and run of the phone's clock (crawling stamps do not keep the link alive; a delay that has lasted 20 s is part of the measure, so a link that has grown slower is not dropped over and over), the client asks for a `pong`, and after 5 s more the session drops the socket and reconnects, as a missed heartbeat does. A frame that arrives out of the order of its stamps, or a `clock` frame for a turn whose state never came, shows the host held a frame back (docs/FAIRNESS.md). A `clock` frame for another hand, or for a turn before the last one its link showed, fails the hand the client is on (`strayFrame`) and is otherwise ignored: the client makes no record for the hand it names, and its per-hand records never give up the hand it is on (`trimHands`). TableHost's default clock is clientClock() and the signal server gives each table steadyClock() (an injected clock only in tests), so stamps never step back. The client also pings the table once a second while it holds a seat on a link that is up, whether or not the table has welcomed it there (`TableClient.holdsSeat`; the link watch runs the same way), and right after each join; the host answers each `ping` at once with its clock (`pong`). Each answer is a fixed point between the two clocks, kept for the hand on show (one per 10 s, the shortest round trip) and saved with the record, with its run of the app and a check figure (`PlayRecord.pongs`, `RunScope`): it measures only the states of the run that made it, so a turn shown late before an app restart or a resume stays late after it. The audit checks that every turn's state arrives on an unbroken link, that the state which starts a turn gives a whole turn clock, and that it is not late: in a hand the table answered pings in, a turn, a claim window or a turn first shown on a new link that reaches the phone more than half its turn clock late (at least 2 s; `lateLimitMs`) against the hand's pongs, its deal and the strongest fixed point of the hands before, less the time the app was paused, is amber, and the table's move after it is judged as one made while the seat had no timely view; a hand with no answered ping is amber (`noAnswer`) when the phone pinged it 5 times, and is measured as before otherwise (17 s against the least arrival offset, 21 s against the round trips of the seat's moves and share). So is a frame no fixed point of its scope bounds, unless it arrived more than the limit after the first ping the phone sent in that scope (`PlayRecord.pingedFrom`, `unanswered`): then the table answered none of that scope's pings sent before it, and the frame is late. A hand keeps the first answer of each scope whatever its round trip, so a frame after it is always bounded. More than 17 s late against the watch's own reference fails the hand when the watch had been measuring the link since before the frame was 8 s late. The table playing over a legal move the seat sent with more of the clock the app showed left (the end the audit holds the table to, `streakEnd`, counted from the turn's first state, or for a move sent after an app restart or resume from the first state of the turn that run of the app saw) than the hand's best round trip and 1.5 s explain losing is amber (`inFlight`; the best round trip measured before the move was sent, in any run of the app or clock era of the host, since a round trip is a duration on the phone's clock: `flightAllowance`), and a move left lying more than 30 s on a link that stayed up, time the app did not run left out, fails. Every fixed point, pongs included, also bounds the host's stamps from below, so a table move, a dropped stamp or a bank taken that the pongs contradict fails. These references start afresh after a phone sleep, an app restart, a forward step of the phone's clock, a server restart the table announces and a new match (a new table, with a clock of its own: the client's era count runs on across matches and the ties carried from the last match are dropped, `resetMatch`), with the next answered ping. The client takes a restart notice only as a returning link's first word, after its `welcome` and the records of missed hands (`TableClient.opening`), never for a hand before the one it is on, and begins at most one clock era for each hand on show (`eraHand`); every other frame that names a hand is taken only where an honest host sends it (`activeHand`, `dealsHand`), and anything else fails the hand the client is on (`strayFrame`, `restartMidLink`). Over the match the client also counts the seat's turns that reached it later than half that limit (`ClientState.turnsShownLate`, `lateCountMs`), which the Fair play screen shows; it is never a verdict. The app shows the seat's own clock as the audit holds the table to it (`TableClient.ownClock`): the turn clock, then the bank, counted by the phone from the state that started the move and placed on its clock by the same fixed points (never later than the least arrival offset of the current scope allows, so a state held on its way before the first answered ping of a new run or clock segment buys it nothing), without waiting for the state that says the bank has started. Both count to one end (`streakEnd`): the rules' clock as the phone tracks it (`clockTrack`), or any later end a state of the move claimed in the host's current clock era, each stated bank less the host's rounding on the screen. So an end the server shows and then takes back still binds the table, and a table move before it fails the hand. Ends of an earlier era are left out: a table move for a seat that owed it across a restart the host announced is amber (`restartClock`).

### Resume after a crash or disconnect

The app has two modes (`Session.mode`): `local` (offline bot tables, hosted on the phone) and `online` (every table with other people, hosted by the game server).

* **Online tables**: `welcome` carries a random rejoin token. The app persists `{signalUrl, roomCode, token}`, where `signalUrl` is the server that hosts that table; on relaunch Home offers *Resume*, which rejoins the room and presents the token. The server's table hands the seat back even if a bot has been standing in and the name changed. A player who rejoins mid-hand still verifies the log, but that hand's audit reads *partial* because their share was not used.
* **Offline bot tables**: `TableHost.serialize()` is written to storage after every change (debounced). On relaunch the host is rebuilt with `restore` and the local client rejoins with its token, landing in the same hand with the same wall.
* **Everyone dropping at once**: the room stays alive for 15 minutes with no peers and the table pauses at the next `hand_over` when no human is connected. A server restart does not end a table either: every hosted table is written to `table_snapshots` as it changes and restored at boot under its own code, and players take their seats back with their rejoin tokens (see "Signaling server" below, and `apps/signal/README.md`, "Persistence").

### Clubs (`apps/signal/src/clubs.ts`, `api.ts`)

A club is a six-character code with an owner, admins and members, house rules (any `RuleSet`), settings (approval required, members may open tables, the bot skill, how many members a match needs to count) and standings. `POST /api/clubs/:code/tables` creates a server-hosted room with the club's rules and registers it; host events keep the table list live and fold `match_over` scores into member standings (only for a match that started with at least as many human members as the club requires: 2 to 4, default 3). Standings are points only, kept per season and all-time; the owner closes a season and its final standings are archived. Owners and admins approve or turn down join requests, remove and ban members, close a table and take a player off one. Every club route takes the caller's bearer session, and the member id is the account the session proves, never an id the client sends. Joining and playing is free; once the store is live, creating a club needs The Four Winds Club, an account owns at most three, and a lapsed plan drops each club's open-table cap to one after a grace period (docs/API.md, "Clubs").

### Puzzle results and leaderboards (`apps/signal/src/puzzles.ts`)

The app keeps a puzzle rating on the device; the server keeps its own, one per account, moved only by answers it verified. Both follow the engine's `movesPuzzleRating`: the daily puzzle and drills move a rating, Puzzle Rush does not (it counts for its own boards). The boards resist scripts only as far as timing allows: puzzles are generated by the engine the app ships, so a script can compute every answer. The server keeps results under the human-time floors off the boards (a daily answer under 3 s, a Rush run averaging under 1.5 s an answer), keeps a Rush run whose answer times no person makes off the boards (from the server's stamp on every answer: 95% right at under 3 s an answer, machine-steady times, more than three answers under 0.8 s, or hard answers no slower than the first fifteen, over 15 answers or more; provisional thresholds), holds a Rush run that solves more than 35 off the board until an admin confirms it in the flag view, flags accounts whose recent results sit at those floors, run perfect at an inhuman pace or have inhuman answer times (an admin clears or confirms the flag), and issues one ranked Rush run a UTC day to an account without Coach Gold. It cannot tell apart a script that imitates a strong player closely, with human-looking variation and the occasional mistake; that is true on every puzzle site (docs/API.md, "What this stops, and what it does not"). With a session the app plays the daily puzzle and Puzzle Rush through the server (apps/mobile/src/logic/puzzleSync.ts, api/puzzles.ts) and shows the server's verdict, time, score and rating wherever it shows the rating; when the server cannot be reached the puzzles play on the device as before, with a note that the result is not ranked. Settings has "Show me on leaderboards" (`leaderboardVisible`). The leaderboard screen (apps/mobile/src/screens/LeaderboardScreen.tsx, rules in logic/leaderboard.ts) reads the boards with the same session: it asks for the daily board of the player's local date key, highlights or pins the player's own row and says so when they are hidden. Opening the daily puzzle starts a server attempt for the local date key the app plays (one per account and key, so reopening keeps the clock); the answer finishes it, and the server regenerates that day's puzzle with the engine, judges the answer against the accepted set, times it with its own clock and ranks the first attempt per key. A ranked Puzzle Rush run is played from the server one puzzle at a time: the server keeps the seed, serves each puzzle only when the previous answer has arrived, judges and stamps each answer as it comes (up to the third strike), and takes the run's time, score and plausibility from those stamps; a lost connection ends the run, unranked, with a note. Ranked puzzles (the daily start and every Rush puzzle) are served as questions (the engine's `puzzleQuestion`: the hand, the table and the choices, no answer, analysis or explanation), and the whole puzzle comes back only with the verdict (docs/API.md, "Questions and reveals"). The app renders a ranked puzzle from its question: each puzzle view (`components/PuzzleView.tsx`, `components/puzzles/*`) takes a question and a judge, reads nothing about the answer until the judge returns the verdict and the revealed puzzle (the question types have no answer fields, so a view cannot), and says it is checking with the server meanwhile; a puzzle made on the device (offline or unranked play, drills) goes through the same views with a judge that answers at once (`localPuzzle` in `logic/puzzle.ts`). With a session the daily puzzle waits for the server's question before it shows the hand; if the server cannot judge the answer after the start, the device judges it against its own copy of the day's puzzle, unranked. Offline or signed out, Rush is seeded and judged on the device and unranked. The checks and the rating step are the engine's (`packages/engine/src/verify.ts`), the same rules the app applies. Boards (the day's puzzle, Rush best for today, this week and all time, and rating) list visible, unbanned, live accounts, globally or for one club the caller belongs to (docs/API.md, "Puzzles and leaderboards"). Data: `puzzle_results`, `puzzle_ratings`, `puzzle_rush_runs` and `users.leaderboard_visible` (migration 0010), `puzzle_daily_attempts` (0011), `ranked` (0012), `puzzle_flags` (0013), `puzzle_rush_answers` and the served puzzle on `puzzle_rush_runs` (0015), `held` on `puzzle_rush_runs` (0018).

### Single-player and learning

`puzzles.ts` generates seeded puzzles in five themes (daily = date seed, Puzzle Rush = run seed + index, difficulty ramps). Easy and medium value and defence puzzles teach the basic rule: keep the most winning tiles (`valueSpeedRule`), and throw by a fixed safety order (`DEFENCE_SAFETY_ORDER`, `defenceOrderRule`). At hard, each seed draws whether the rule should fail (`VALUE_HARD_SIZE_SHARE`, `DEFENCE_HARD_READ_SHARE`, both one half): a value puzzle is then built from a pure flush with a two-tile wait or from pongs (concealed pongs count), so the bigger hand wins, and a defence table keeps a live honour in the hand and gives the threat discards across a gap of three (筋) from a suited tile, so only reading the discards finds the safer tile. The generator keeps trying, from the seed's own random stream, until the judge agrees with the draw; the judge itself (expected score within `VALUE_TOLERANCE`, the deal-in model checked against the exact count) is the same at every difficulty. On 16 November 2026 the rule was wrong in about half of hard puzzles (value 48%, defence 47% over 400 seeds) against 6% and 8% before, easy and medium unchanged, and a hard value puzzle takes about 8 ms to generate (99th percentile about 70 ms) and a hard defence puzzle about 3 ms (99th percentile about 15 ms), so the server re-judges a 180-puzzle Rush run in about a second. That left a two-line rule, "take a discard holding a pattern of 4 台 or more if it keeps at least half the most winning tiles, else keep the most winning tiles" (`valuePatternRule`), right on 86% of hard value puzzles (257 of 300), because every bigger hand that won did so with 碰碰胡 or 清一色 and every speed win was against a smaller or slower hand. Since 17 November 2026 most hard speed wins (`VALUE_HARD_TRAP_SHARE`, four in five) are against such a pattern that keeps half the tiles and is still not worth them (大三元, 小三元, 大四喜, 小四喜, 四暗刻, 五暗刻, 碰碰胡, a flush), built from a flush, pongs or three of a family of honours, and the explanation names the pattern the tempting discard goes for; the bigger hands that win do so with 清一色, 碰碰胡 and 四暗刻 (each in a quarter to two fifths of them). A daily takes about 8 ms (median; the slowest of 365 about 150 to 210 ms, the first one, before the shanten tables fill), a hard puzzle about 4 ms (slowest about 50 ms). The seventh pass's engine checker then read the hand another way: take out the complete sets (pongs first, then runs from the low end of each suit) and throw the leftover with the fewest neighbours among the leftovers. One of a pair inside a run, often a rule-proof hand's answer, is a leftover single to that read, so it was right on 268 and 274 of 365 dailies (2027 and 2029) and 217 of 300 hard puzzles. Since 19 November 2026 a medium or hard rule-proof hand must also beat that read, with the sets taken out three ways (pongs first, runs first, the most sets; `ruleOfThumbPicks` with `sets`), the walk may take 350 steps for it, and more medium and hard seeds draw a rule-proof hand (85% and 75%). The read is then right on 207 and 217 of those dailies and 117 of those hard puzzles; on 300 more hard seeds every rule measured is under 43%. The easy dailies (Monday, Wednesday, Friday) keep the older rule-proofing and the read is right on about three in four of them: beating it there took a median over 100 ms on this machine and made the other rules stronger. `test/puzzle_rules.test.ts` measures 12 sets-first rules as well (`setsFirstRules`): under 48% of hard puzzles, under half of the medium and hard dailies, under 62% of all dailies. A hard puzzle now takes about 13 ms (median), a daily about 12 ms; the slowest of 365 dailies about 150 to 200 ms. The shanten table of a suit is computed about 2.4 times faster since then (`overlapTable` in `hand.ts`, checked equal to the old one on every count vector of a suit and of the honours). Every daily and hard Rush and drill puzzle changed again, which is acceptable before launch. Over the 365 dailies the decisions are now: isolated 118, break a pair 140, compare 38, weaker 搭子 46, a lone tile worth keeping 22, keep the pair 1. `review.ts` replays a finished hand from its audit (snapshot + seed + log) and grades every decision against the pro bot. Bots come in three skills with distinct policies.

**Bot tiers and the strength gate.** Beginner plays for tile efficiency with mistakes and never measures danger. Club is efficient, claims when a claim helps, and leans a little away from a seat it reads as ready. Pro adds three things to that: a per-tile deal-in estimate (`readOpponents`, `waitChance` in `bot.ts`), a fold when it is two or more tiles from ready and a seat is probably ready, and 台 terms (value-honour pairs and pongs, a flush once it is in reach). CI runs `npm run sim -- --gate` (`packages/engine/scripts/simulate.ts`, rules in `packages/engine/test/helpers/gate.ts`): 2,000 fixed seeds, each played three times with three Club bots around a rotating test seat (Pro in the seat, Club in the seat, and Pro with its deal-in and 台 terms switched off in the seat), compared hand by hand with `packages/engine/test/fixtures/bot-gate.json`. The seeds are fixed, so a run differs from the reference only where the bots changed; the gate fails when any hand scores differently from the reference in either series (the bots play differently without a new reference), when Pro minus Club, or Pro minus Pro-without-the-terms, drops more than 1 point a hand below the reference, when Pro is behind Club at 95%, or when the terms cost points at 95% or change no hand. A change to how the bots play is made on purpose and in two steps, which the failure message spells out: measure it first on held-out seeds the gate does not use (`npm run sim -- --ladder pro 3000 --seed <a fresh prefix>`, and `--ladder club` for Club, comparing the paired difference before and after), then record a new reference with `npm run sim -- --gate --record`, read its diff and commit it with the measurement. The strength checks matter when a reference is recorded: they refuse a Pro behind Club or terms that cost points, whatever the new reference says. Before the hand-by-hand rule, tried against five altered Pros (`--weights`), the gate failed one with the deal-in terms off (1.18 points a hand below the reference), one that folds far too readily (4.69 below) and the old claim threshold that lost to Club (11.21 below, behind Club at 95%), failed one with every term off only because the terms then change no hand, and passed one with the 台 terms off (0.52 higher) and, in the fifth assessment, one with Pro's and Club's defence off (`{"proFold":0,"proLean":0,"clubDefence":0}`: 968 of 2,000 hands changed, both means inside the allowance). Each of these now fails: the defence-off bots change 1,019 of the 2,000 hands.

**Bots at a 嚦咕嚦咕 table.** With `liguTai` above 0 every tier weighs seven pairs and a triplet beside five sets and a pair while its hand has no melds (`liguPath` in `hand.ts`, `BOT_WEIGHTS.ligu` and `liguMargin` in `bot.ts`); the rules side is in `docs/RULES.md`. `npm run sim -- --ligu <n>` measures it: each tier plays a rotating test seat among three Club bots that know the hand, once knowing it and once blind to it, on the same seeds (17 November 2026, `liguTai` 4). Following whichever hand was nearer (margin 0) cost Club 2.71 points a hand (standard error 1.27, 95% interval -5.19 to -0.22) over 4,000 paired hands on seed prefix `u11ligu`, behind at 95%; Beginner (-1.91, se 1.19) and Pro (-0.24, se 1.21) were level. Requiring 嚦咕嚦咕 to be more than one step nearer (margin 1) was chosen on prefix `u11tune` (Club +0.15 against -1.16 at margin 0, 2,000 hands) and reported on 4,000 held-out paired hands per tier, prefix `u11report`: knowing minus blind is +0.20 points a hand for Beginner (se 0.62, interval -1.01 to +1.41), +0.14 for Club (se 0.68, -1.19 to +1.47) and -0.29 for Pro (se 0.55, -1.36 to +0.78), so no tier is worse at 95% and none is measurably better. A table of four Club bots that know the hand wins 7.0 hands in 1,000 by 嚦咕嚦咕 (4.8 with Pro and 6.0 with Beginner in the test seat), where blind bots won none in these runs or in unit 6's 300 matches; illegal moves 0. With the rule off the bots decide exactly as before: the gate shows 0 of 2,000 hands different and `test/ligu_bots.test.ts` replays 300 states whose bot and coach decisions were recorded before the change.

What the gate shows today, and what it does not: Pro minus Club is +1.04 points a hand (standard error 4.36, 95% interval -7.51 to +9.59), so Pro is not clearly ahead of Club on these hands. Pro minus Pro without the terms is -2.23 points a hand (standard error 3.47, interval -9.03 to +4.57): no measurable gain from the deal-in and 台 terms. The gate reports this on every run and does not fail on it; until a Pro puts the second comparison ahead at 95%, product copy should not promise more than "Pro reads danger and may fold".

A retune was tried on 12 November 2026 and changed nothing. A sweep of 33 weight settings over 3,000 paired hands found none ahead of today's Pro at 95%; the one candidate named in advance (a gentler flush chase) was then played on 8,000 held-out hands and was not ahead (+0.44 points a hand, standard error 0.47), and the best exploratory setting failed its own confirmation on a third set of 8,000 (+0.33, standard error 0.60). Folding more trades deal-ins for wins at about break-even, which says the danger estimate does not yet separate dangerous tiles from safe ones well enough for a fold to pay. ### Signaling server (`apps/signal`)

One Node process: a WebSocket server for tables and an HTTP API, over Postgres or, with no database configured, in-memory repositories (`src/repos`). `docs/API.md` is the reference for every route and frame; `apps/signal/README.md` for configuration and limits.

* **Sockets.** Frames: `hello` (the first frame, carrying the session token), `create`, `join`, `to` (relay), `leave`, `ping`, and `queue` / `leave_queue` for quick match. `create {hosted:true}` instantiates a `TableHost` inside the server bound to a `ServerTransport`, so the room's host peer is the server; this is how every online table runs. The server binds the account that `hello` proved to the seat: a table `join` always carries the verified user id and the account's display name, whatever the client sent.
* **Accounts and sessions** (`src/auth`). A device starts as a guest account (a random id and a secret kept in the phone's secure storage) and can link Sign in with Apple or Google; a guest that signs in to an existing account is merged into it. Sessions are opaque tokens stored as peppered hashes, sliding 30 days. Deleting an account scrubs it at once and purges the row after 30 days; what outlives it (scores without the name, purchase records, reports) is listed in docs/STORE_COMPLIANCE.md. On the device: the birth year is sent only when the server has none; a name the server refused is masked until the player changes it; a ban is remembered for 24 hours before the app asks the server again; and "Start fresh" on a signed-out device asks the server for the new guest before it sets the old identity aside (docs/API.md, "what the app relies on").
* **Persistence** (`src/persist.ts`, `migrations/`). Clubs are held in memory and written behind each change; every hosted table is snapshotted as it changes and restored at boot. A snapshot is restored only when it passes the engine's checks (`src/restoreCheck.ts`): rules the engine accepts as they stand, and a hand that the engine replays from its deal and moves to exactly the stored state, or between hands the last hand its record published. One that fails is never restored as a live table; it is logged and kept as `damaged`, with the reason, for an admin (`GET /api/admin/tables/damaged`, migration 0021) for 30 days, and its players find the table gone. Room lifetimes: a table with a seated human and nobody connected is kept for 15 minutes; a lobby opened over the socket closes as soon as it empties; a started quick-match table closes 2 minutes after its last player dropped.
* **Quick match and moderation** (`src/matchmaking.ts`, `src/moderation.ts`). The queue seats strangers four to a table, the closest quick-match ratings together first when more are waiting than one table holds (a full table is seated at once within a 200-point spread, which widens to 1,000 by the fill time, so a wide table waits a few seconds for closer players but never past the fill time), fills with Club bots after 20 seconds, never seats two accounts where either blocked the other, and refuses banned accounts and accounts without a birth year of 18 or over. Each table is charged to its players' create allowance (one table per account every 10 s), so a player who left a table moments ago waits up to 10 s to be seated again: on purpose, and its `queue_status` says how long (`cooldownMs`), which the Quick match screen shows. A player who leaves a table before it started is let go: the table stops waiting for it and it may queue again. Each account has a quick-match rating (`src/tableRating.ts`, table `table_ratings`, migration 0016): a finished quick-match match with two or more humans moves each human's rating by an Elo update over every pair of humans, scored by their final scores (K 16, and 40 for an account's first 20 matches); bots never count, and a table opened for two accounts that queued from one address or one device moves nobody's rating (otherwise a second account could lose on purpose to lift the first above the strangers). It is merged and purged with the account like the puzzle rating, `GET /api/me` carries it, the account card shows it and the match-over card after a quick match shows the change. The anti-collusion counts survive a restart on Postgres (migration 0017): how often each pair of accounts sat together at quick-match tables, and at how many from one IPv4 address (`quick_match_pairs`, written by the matchmaker, read by the admin view), and each club's daily join allowance per address and per device (`club_join_allowances`: the token bucket as it stood, keyed by a salted hash of the address or install id, loaded when the club registry loads and written before a join is answered). The hourly join allowances, per address across all clubs and per club for established and for new accounts, are kept the same way (`club_join_hours`, migration 0020; an address only as its salted hash), so a restart or a move to another machine resets none of them, and stored buckets that have refilled are pruned every hour. With the in-memory store they all stay in the process. Players report and block each other; moderators (an admin token) dismiss, warn, mute or ban, and a ban covers the account's devices. There is no free text at a table: phrases and emotes are ids. Display names, club names and descriptions pass a blocklist.
* **Wallet and store** (`src/wallet.ts`, `src/catalog.ts`, `src/reconcile.ts`). Entitlements are decided on the server from RevenueCat webhooks, stored raw and applied once; diamonds buy cosmetics only. A refund takes back only the period its transaction paid for (docs/MONETISATION.md). A purchase's price is recorded only when the `purchases.price` column can hold it (0 to below 10^10 at four decimals), and as null otherwise, so the credit never fails over the price. A `TRANSFER` moves the purchases behind the plans it moves, and a subscription event that still names the old account (a refund or renewal delivered late) is applied to the account that holds the purchase now, found by its transaction or original transaction id.
* **Repositories** (`src/repos`). `types.ts` declares every repository; `memory.ts` implements them in memory and the Postgres ones are split by area. `pg.ts` holds `createPgRepos`, which assembles them, and the transaction runner; `pgShared.ts` the uuid check (`isUuid`, re-exported from `pg.ts`) and the value conversions; `pgUsers.ts` users, sign-in identities, sessions and devices; `pgWallet.ts` the wallet (ledger, purchases, entitlements) and the store event log; `pgModeration.ts` reports, blocks and bans; `pgClubs.ts` clubs and their join allowances; `pgTables.ts` table snapshots, match results, the table rating and the quick-match pair counts; `pgPuzzles.ts` puzzle results and ratings, Rush runs, daily attempts, puzzle flags and the leaderboards. Every statement is a constant string with `$n` placeholders.
* **Push** (`src/push.ts`). Expo push for "club table opened", "join request approved" and "your table is waiting", to devices whose owner allowed notifications.
* `/health` returns counts, the storage in use, snapshot write counters and the action-to-state latency (docs/OBSERVABILITY.md).

## Determinism rules

* Never read `Date.now()` or `Math.random()` inside the engine. Randomness enters only through the seed.
* `applyAction` must not mutate its input (we clone via JSON; states are small).
* Any new rule must be covered by `scoring.test.ts` or `game.test.ts` and must keep `replay` byte-identical. A rule that changes a 台 item or a payment must also be taught to the scoring oracle (`packages/engine/test/helpers/oracle.ts`, see docs/RULES.md, How the scorer is checked), which is written from docs/RULES.md and checks the scorer on 58,000 generated wins.
